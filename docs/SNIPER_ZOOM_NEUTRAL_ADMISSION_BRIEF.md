# Astra zoom neutral-admission decision

One design question before connecting native zoom: how to distinguish physical zoom-button release from desiredZoom=false caused by tracking/wheel/equip suppression across network retention? Read-only design review, <=900words prioritized choice/gates. No edits/agents/runtime. Existing Astra-approved codec is a completed transport slice, not approval of zoom enablement.

Verified source: PosePacket currently has desired zoomMask and historical pulseZoomMask, plus primary-trigger physicalDownMask/releasedSerial[2]. PeerState::acceptPose advances primary release witnesses only for an actual unblocked/tracked incoming neutral sample with newer primary serial. invalidateTracking/invalidateWeaponGeneration clear witnesses; preserving desired false alone is deliberately not proof of trigger release. zoomMask likewise will be false on invalid/equip/wheel/recenter; reusing it as physical release would infer a release that did not happen. Current producer still sends zero zoom fields. Native weapon identity is actual owned handle/type, not wire type13 alone. Same-type replacement can invalidate intent independent of trackingGeneration.

Reference: local neutral gates already protect primary triggers and distinct native lifecycle callbacks own gun state. All new zoom desired state must stay in existing Snapshot/Authority/ordered interval; native IsZooming remains native state truth. Historical shot zoom (including historical zero) must remain frozen for the entire consumed interval, using intervalZoomMask after admitted pulses. Rejected pulses cannot override latest desired. No zoom tap queue, native handles wire or new transport. Teleport absent.

Minimal alternatives:
A. Trust local sender's neutral-gated desired zoomMask; server reset requires later desired0 before accepting1. Smallest wire change (already implemented), but cannot distinguish suppressed0/physicalrelease, same-type replacement/dead input later may inherit a held button.
B. Main lean: extend existing PosePacket with zoomPhysicalDownMask and zoomReleasedSerial[2]; derive these ONLY from actual new focused/tracked OpenXR click samples, independent of desired suppression. Extend existing per-hand PeerState neutral admission narrowly for zoom, invalidated by existing capability/tracking/weapon boundaries. Existing reliable ordering/credit retention remain unchanged; desired and retained fire causality remain existing fields. Source wire increment before any packaging, no layout-preserving silent semantics. Reuse existing invalidation entrypoints, not a separate connection/zoom policy object. Native adapter still revalidates actual owned sniper/hand/lifecycle.

Host input: contextual per-hand axis-click zoom, four profiles (Touch/Index thumbstick, Vive trackpad, Microsoft thumbstick). New raw Zoom bit64 and profile-specific provenance bits ZoomConflictsJump128/ZoomConflictsSprint256 only for actual shared physical controls. Bind a zoom action alongside existing bindings; query active interaction profile per hand for collision provenance; unknown profile still carries raw physicalZoom with no speculative native Jump/Sprint consumption. Native consumer consumes only proven conflicting click when actual sniper zoom handling owns that hand, not distinct Jump buttons. Recenter/wheel/loss cancel desired; retain raw physical click so resumption must observe neutral. Semantic IPC bump7 if/when action input changes; current component remains IPC6.

Native lifetime: initially-first-person and no unmanaged zoom adoption; direct originalActivate/Deactivate/baseheld calls; field-free predicates retain true BC. Exact before-toggle cleanup and PutDown/Delete events prevent reactivation; retain off token through admitted native sound-stop normal tail or sound-source deletion. Activation admission still needs native state/lifecycle and stock client/server caller evidence; these investigations are independent, no enablement here.

Please select A/B or an even smaller sound adapter. Challenge whether extra neutral state is necessary, whether release serial metadata suffices across delayed snapshots/weapon transitions, and how retained historical shot zoom should be admitted when raw zoom button is now up. Primary shot release admission still applies. Need a concrete rule, not a second scheduler/protocol.

## Primary-source input correction and smaller option

Khronos documents that bound-source paths are opaque and intended for localized-name queries, so no path-content/equality inference is justified for collision provenance: [current core manual](https://registry.khronos.org/OpenXR/specs/1.1/man/html/xrEnumerateBoundSourcesForAction.html). Current interaction profile also does not establish user remapped physical bindings. Do not implement either speculative inference.

Smaller candidate: reuse the exact existing logical click action boolean as the contextual zoom stream (Sprint per hand for Touch/Index/Microsoft and Vive left; Jump action right for Vive right). RawZoom and corresponding conflict provenance derive from that SAME sampled action value in code. Remapping moves that contextual action together; no separate Zoom action or independent physical-source inference exists. Profile selects the logical stream, not a physical collision claim. Labels/docs must disclose contextual Sprint/Jump versus zoom behavior. Distinct Jump actions on other profiles remain native. Unknown profile can conservatively use only the Sprint contextual stream. No implementation yet; Astra should choose this or a sound simpler alternative.
